# Additional backend endpoints needed to complete the project

Prepared 31 October 2026 by comparing the original product requirements, the supplied API reference, and backend route registrations. Local-only placeholder screens have now been removed; this document preserves their outstanding backend requirements. **The reference is complete for the existing 69 routes, but the backend is not feature-complete for this frontend.** Every route below is a proposal, not an existing callable endpoint. Names can be adjusted before implementation.

## Priority 3 — operational controls if part of launch scope

- `GET /api/auth/sessions`, `DELETE /api/auth/sessions/:id` for individual device revocation. Logout-all already exists; do not build a second equivalent endpoint.
- MFA enrollment/confirmation/challenge/recovery and SSO only if required by the security screen's promises. Existing passwords and refresh sessions are not MFA.
- Async job status/cancellation for imports, DNS provisioning, bulk operations, reports and retention. Reuse one job contract rather than a separate progress scheme per screen.
- If routing still exposes quarantine actions: quarantine list/detail/release/delete APIs, with durable reasons and auditable release. The earlier product requirements included quarantine routing; no server implementation is supplied.
- Shared mailbox/delegation, migration, backup/restore, legal hold, e-discovery and provider configuration are separate product scope decisions; do not treat them as already delivered by the basic mail API.

## Existing routes that need strengthening, not duplicate endpoints

1. **Workspace lists stop at 1,000 rows.** Add pagination/cursors and totals to GET tasks/notes/events. Optional single-item GETs support deep links without reloading every row. The UI explicitly reports the current limit.
2. **Empty-page totals are inaccurate.** Message/contact SQL uses window counts from returned rows. An out-of-range page reports zero even when earlier pages contain records. Compute an independent count or provide a stable cursor contract; test deletion of the last item on the last page.
3. **Company-only contact query needs a database test.** `contacts.js` retains the initial user parameter while `scope=company` does not reference `$1`. This is a source-level concern already noted by the reference; verify/fix bind typing against PostgreSQL. The current UI uses `scope=all` and does not depend on the company-only branch.
4. **Label undo is not an exact snapshot.** Return only associations actually added/removed, or a server-issued undo token. Existing inverse actions can remove previously existing labels or restore pairs never present.
5. **False filters are asymmetric.** `unread=false` selects read mail, while `starred=false` and `hasAttachments=false` currently do not filter. Implement negative filtering or clearly advertise the limitation in the schema.
6. **Consistent errors and limits.** Normalize 429/upload/constraint errors to the documented envelope, validate inbound-log limits as positive integers, and return explicit validation failures for invalid event ranges/dates. Keep refresh/login/reset limits covered by tests.
7. **Durable send and sync status.** Provide operation IDs for long-running/ambiguous sends and Zoho sync. The current sync POST runs synchronously; the UI's request timeout can expire while server work continues. Check GET sync status before retrying.
8. **Session/cookie deployment verification.** Test real browser CORS, cookie rotation, inactive users and logout-all across the actual frontend/API hosts. Mocked tests do not establish that production cookies or SES work.

## Frontend-only backlog — backend support already exists

These do not justify new backend endpoints: folder rename, label rename/color editing, richer multi-label display, thread view, original `.eml` download, batch identity inspection, company-contact creation by admins, task priority/notes, pinned/color notes, all-day event editing, and server-filtered workspace search. The API adapter already exposes the required routes. Full rich-text composing is also a frontend editor change; the draft API accepts HTML/text.

## Shared contract for proposed work

Use UUID resource IDs, ISO timestamps with offsets, validated enums, owner/organization scope, server-side admin checks and stable pagination. POST returns 201 plus a singular resource, PATCH returns the updated resource, DELETE returns 204 where no result body is needed. Use `{error, details?}` consistently; distinguish 400, 401, 403, 404 and 409. Validate authorization on each item in a bulk request, define whether bulk writes are atomic, add idempotency for jobs, and use version checks where writes can conflict. Do not reuse UI-local IDs or demo role names as a server authority.

## Delivery sequence and definition of done

1. Establish a reachable test environment and run the existing backend tests against a dedicated PostgreSQL database; then verify the now-connected core mail/account/workspace flows in a real browser.
2. Implement Stores + memberships + audit if those are the next operational requirements; add monitoring with explicit access policy and audited reads.
3. Implement hosted-domain provisioning, groups and routing with their actual transport/worker effects; then reports, quotas and policy enforcement.
4. Add optional productivity features and advanced account controls according to product scope.

For each feature, completion means schema/migrations, permission and validation tests, list/detail/mutation contracts, server side effects, frontend integration with loading/error states, persistence after reload, and a real end-to-end test. A route stub or successful mocked response alone does not complete the feature.
